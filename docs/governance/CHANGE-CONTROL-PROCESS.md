## 1. 概述

本文档定义 GITS 知识工程项目 HLD 冻结后的变更控制流程，确保所有基线变更经过规范评审和审批，维护项目架构完整性和交付可控性。

## 2. 变更请求提交

### 2.1 变更请求模板

提交变更请求时须填写以下信息：

```
变更请求编号：CR-YYYY-NNN
提出人：
提出日期：
变更类型：□ 重大  □ 一般  □ 轻微
变更标题：（一句话描述）
变更描述：（详细说明变更内容和原因）

影响范围：
  □ 架构设计（ADR 变更）
  □ 模块边界（新增/删除/合并模块）
  □ 端口接口（Port 接口签名变更）
  □ 适配器实现（Adapter 替换或新增）
  □ 合同规范（CTR-* 合同变更）
  □ 数据模型（数据库 Schema 变更）
  □ API 接口（OpenAPI 合同变更）
  □ 其他：______

影响分析：
  - 受影响模块：
  - 受影响合同：
  - 受影响 ADR：
  - 估算工作量（人天）：
  - 估算风险等级：□ 高  □ 中  □ 低

替代方案：（是否有不修改基线的替代方案）
回退方案：（变更实施后如需回退的方案）
```

### 2.2 提交渠道

- 变更请求提交至 CCB 主席（或指定代理人）
- 提交方式：项目协作平台或邮件
- 提交截止：CCB 例会前 3 个工作日

## 3. 影响分析要求

### 3.1 必须分析的内容

| 分析维度 | 要求 |
|---------|------|
| 架构影响 | 是否违反六边形架构原则、是否改变模块边界、是否影响端口-适配器契约 |
| 合同影响 | 是否影响 CTR-* 合同的向后兼容性 |
| 数据影响 | 是否涉及数据库 Schema 变更、是否需要数据迁移 |
| 测试影响 | 回归测试范围、新增测试用例数量估算 |
| 进度影响 | 对当前迭代和后续迭代的影响 |
| 资源影响 | 所需人力、环境、工具变更 |

## 4. 审批流程

### 4.1 标准审批流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 变更请求  │───→│ 影响分析  │───→│ CCB 评审  │───→│ 批准/拒绝 │───→│  实施    │───→│  验证    │
│  提交    │    │  评估    │    │  会议    │    │  决策    │    │  执行    │    │  确认    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     ↓               ↓               ↓               ↓               ↓               ↓
  CR登记         IA报告         评审记录         决策通知        实施记录        验证报告
```

### 4.2 各阶段说明

| 阶段 | 负责人 | 产出物 | 时限 |
|------|-------|-------|------|
| 变更请求提交 | 变更提出人 | CR 表单 | — |
| 影响分析评估 | 技术代表 + 相关模块负责人 | IA 报告 | 3 个工作日 |
| CCB 评审 | CCB 全体成员 | 评审记录 | 下一次 CCB 例会 |
| 批准/拒绝决策 | CCB | 决策通知 | 评审后 1 个工作日 |
| 实施执行 | 变更提出人 + 开发团队 | 代码变更 + ADR 更新 | 按迭代计划 |
| 验证确认 | QA 代表 | 验证报告 | 实施完成后 2 个工作日 |

### 4.3 决策结果

| 决策 | 含义 | 后续动作 |
|------|------|---------|
| 批准 | 变更获准实施 | 纳入迭代计划，分配资源 |
| 拒绝 | 变更不予实施 | 记录拒绝理由，通知提出人 |
| 推迟 | 变更暂缓，待后续评审 | 记入待评审队列，指定下次评审时间 |
| 需补充信息 | 影响分析不充分 | 退回提出人补充，重新提交 |

## 5. 紧急变更流程

### 5.1 紧急变更定义

满足以下任一条件可申请紧急变更：

- 生产环境故障导致系统不可用
- 安全漏洞需立即修复
- 数据完整性受损需紧急修复
- 监管合规要求需立即响应

### 5.2 紧急变更流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 紧急变更  │───→│ CCB 主席  │───→│  实施    │───→│ 事后补审  │
│  申请    │    │ 快速审批  │    │  执行    │    │  确认    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
     ↓               ↓               ↓               ↓
  紧急CR         主席批准        临时修复        下次CCB例会
```

### 5.3 紧急变更规则

1. CCB 主席可在 24 小时内单独批准紧急变更
2. 紧急变更实施后须在下一次 CCB 例会进行事后补审
3. 事后补审可追认、修改或回退紧急变更
4. 紧急变更须在实施后 1 个工作日内补交完整的影响分析报告
5. 每个迭代周期内紧急变更不超过 2 次，超出需 CCB 全体讨论

## 6. 基线变更分类

### 6.1 分类标准

| 分类 | 定义 | 示例 | 审批要求 |
|------|------|------|---------|
| **重大变更（Major）** | 影响架构核心原则、模块边界或关键合同 | 新增模块、改变六边形架构依赖方向、API 合同不兼容变更 | CCB 一致同意 |
| **一般变更（Normal）** | 影响模块内部实现或适配器，不改变架构边界 | 新增端口方法、替换适配器实现、新增 ADR | CCB 多数通过 |
| **轻微变更（Minor）** | 不影响架构和合同，仅涉及实现细节 | 代码重构、配置调整、文档修正 | CCB 主席批准 |

### 6.2 分类判定

变更分类由技术代表初步判定，CCB 评审时确认。如对分类有争议，按更高等级处理。

## 7. 变更实施与验证

### 7.1 实施要求

- 变更实施须遵循项目编码规范和分支策略
- 涉及 ADR 变更的须同步更新 ADR 文档
- 涉及合同变更的须同步更新合同文件和 `CONTRACT_INDEX.yaml`
- 实施完成后须通过代码评审

### 7.2 验证要求

- QA 代表确认变更通过回归测试
- 技术代表确认变更符合架构原则
- 验证通过后关闭变更请求
